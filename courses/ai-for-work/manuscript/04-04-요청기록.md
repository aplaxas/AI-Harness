# 4.4 잘된 요청과 수정 이유 남기기

> [목차](index.md) · 이전: [4.3 원문과 결과를 대조하기](04-03-원문대조.md) · 다음: 5.1 수신자와 목적에 맞는 문서 만들기 (작성 예정)

4.1이나 4.2에서 업무 하나를 끝냈다. 요청을 쓰고, 고치고, 대조하고, 마무리했다. 이 절에서는 그 과정을 짧게 기록으로 남긴다. 다음에 같은 일을 할 때 빈 화면에서 시작하지 않기 위해서다. 1.4에서 "잘된 요청은 따로 저장해 둔다"고 한 것을 여기서 구체적으로 한다.

## 왜 남기나

대화창에는 이미 기록이 있다. 그런데 대화 기록만으로는 부족하다.

- **어느 요청이 잘된 것인지 표시가 없다.** 대화에는 처음 요청, 고친 요청, 다시 고친 요청이 다 섞여 있다. 다음에 무엇을 다시 쓸지 찾으려면 대화를 처음부터 읽어야 한다.
- **왜 고쳤는지가 남지 않는다.** 대화에는 "광고비 축소는 논의로 옮겨 줘"라는 문장만 있다. 그 결과 요청의 조건을 바꿔야 하는지, 이번 메모에만 해당하는 일인지는 적혀 있지 않다.
- **대화가 사라질 수 있다.** 1.5에서 본 임시 대화를 썼거나, 보관 기간이 지났거나, 내가 지웠을 수 있다.

그래서 나는 대화와 별개로 내 문서에 남긴다. 길게 쓰지 않는다. 한 건에 표 하나다.

## 무엇을 남기나

아래 항목을 한 묶음으로 남긴다.

| 항목 | 적는 것 |
| --- | --- |
| 업무 | 무슨 일인가. 예: 주간회의 메모 → 회의록 |
| 날짜와 도구 | 언제, 어느 앱과 모델로 했나 (1.3) |
| 넣은 자료와 지운 것 | 무엇을 넣었고 무엇을 바꾸거나 지웠나 (1.5) |
| 처음 요청 | 처음 보낸 요청 그대로 |
| 고친 점과 이유 | 무엇을 고쳤고 왜 고쳤나 |
| 최종 요청 | 다음에 그대로 쓸 수 있게 다듬은 요청 |
| 대조 결과 | 누락·추가·바뀜이 몇 개, 무엇이었나 (4.3) |
| 내가 직접 판단한 것 | AI에 맡기지 않고 내가 정한 것 |
| 다음에 바꿀 것 | 다음번에 처음부터 넣을 조건이나 자료 |

이 중 가장 중요한 칸은 "고친 점과 이유"와 "최종 요청"이다. 최종 요청은 다음에 복사해서 쓸 것이고, 고친 이유는 그 요청이 왜 그 모양인지 알려 준다.

## 수정 이유를 쓰는 법

"더 좋게 고쳤다"는 이유가 아니다. 무엇이 문제였고, 그 문제가 어디서 왔는지 쓴다. 나는 문제가 어디서 왔는지를 네 가지로 나눠 본다.

| 원인 | 뜻 | 다음에 고칠 곳 |
| --- | --- | --- |
| 요청 | 조건이나 결과 형식을 말하지 않았다 | 요청 |
| 자료 | 필요한 자료를 넣지 않았거나, 지우다가 필요한 정보까지 지웠다 | 넣는 자료 |
| 결과 | 요청에 분명히 있었는데도 결과가 어겼다 | 대조할 곳 |
| 내 기준 | 결과를 보고 나서야 내가 원하는 것을 알았다 | 요청, 또는 예시 |

이렇게 나누면 다음에 무엇을 해야 할지가 정해진다. 원인이 요청이면 최종 요청에 조건을 더한다. 원인이 결과면 요청을 고쳐도 다시 생길 수 있으니 4.3에서 그 자리를 먼저 본다. 원인이 내 기준이면 2.3처럼 예시를 함께 넣는 방법을 생각한다.

여기서부터는 내 해석이다. 이 구분에서 가장 놓치기 쉬운 것은 "내 기준"이다. 결과가 마음에 들지 않으면 AI가 틀렸다고 생각하기 쉽다. 그런데 다시 읽어 보면 처음 요청에 그 기준이 없었던 경우가 있다. 이것을 적어 두면 요청이 다음번에 한 줄 더 좋아진다.

## 예시 기록

4.1의 회의록 실습을 기록하면 이런 모양이 된다. 설명을 위해 만든 예시다. 실제로 해 본 기록이 아니다.

| 항목 | 내용 |
| --- | --- |
| 업무 | 마케팅 주간회의 메모 → 팀 공유용 회의록 |
| 날짜와 도구 | (날짜), (앱과 모델) |
| 넣은 자료와 지운 것 | 메모 7줄. 이름 4명은 참석자 A~C와 작성자로, 광고비는 [광고비]로 |
| 처음 요청 | "아래 메모를 회의록으로 정리해 줘" |
| 고친 점과 이유 | ① 할인 행사 날짜가 결정으로 들어감 → 원인: 요청. 결정의 기준을 말하지 않았다. ② 물류팀 문의에 담당자가 채워짐 → 원인: 요청. 빈칸 처리 방법을 말하지 않았다. ③ 다음 회의 날짜가 빠짐 → 원인: 요청. 기본 정보 칸을 정하지 않았다. ④ 메모에 없는 "광고 효과 분석 보고"가 할 일로 붙음 → 원인: 결과. "메모에 없는 내용은 더하지 않는다"를 넣은 뒤에도 생길 수 있으니 대조할 때 먼저 본다 |
| 최종 요청 | 4.1의 요청 전문 |
| 대조 결과 | 그대로 3, 누락 1, 추가 1, 바뀜 2 (4.3의 예시 표) |
| 내가 직접 판단한 것 | 물류팀 문의 담당자는 정하지 않고 "미정"으로 공유. 공유 대상 확인 |
| 다음에 바꿀 것 | 지난 회의록 하나를 예시로 함께 넣어 본다 |

이렇게 남겨 두면 다음 주 회의록은 "최종 요청"을 복사하고 메모만 바꿔 넣는 데서 시작한다. 대조할 때도 지난번에 바뀜이 나온 자리, 곧 결정과 논의의 구분과 담당자 칸을 먼저 본다.

## 어디에 둘까

처음에는 문서 하나면 충분하다. 업무마다 문서 하나를 만들고, 할 때마다 표를 하나씩 위에 더한다. 메모 앱이든 워드 파일이든 상관없다. 기준은 두 가지다. 다음에 그 업무를 할 때 바로 열 수 있는 곳이어야 하고, 1.5에서 지운 실명이나 숫자를 다시 적어 넣지 않아야 한다. 대응표는 이 기록에도 넣지 않는다.

기록이 쌓이면 파일 이름과 폴더를 정리할 필요가 생긴다. 그 방법은 9장에서 다룬다.

## 이 기록이 다음 단계가 된다

여기까지가 1부다. 작은 업무 하나를 안전하게 끝내고, 그 과정을 기록으로 남겼다.

이 기록은 3부에서 다시 쓴다. 같은 업무를 몇 번 하면 최종 요청 안에서 매번 같은 부분과 매번 바뀌는 부분이 나뉜다. 회의록이라면 "결정은 합의가 분명한 것만"이라는 조건은 매번 같고, 메모는 매번 바뀐다. 매번 같은 부분을 따로 떼어 두는 것이 10장의 **공통 지침**이다. 공통 지침은 AI 도구에 미리 적어 두어 모든 요청에 자동으로 붙게 하는 설명이다. 여기서 한 걸음 더 나아가 요청과 절차와 확인 기준을 묶어 이름을 붙여 두고 필요할 때 불러 쓰게 만든 것이 12장의 **스킬**이다.

지금 남기는 표 한 장이 그 재료다. 그리고 "고친 점과 이유"에 쌓인 실패 사례는 17장에서 결과의 품질을 판단하는 기준을 만들 때 다시 쓴다.

> ✍️ **[채우기]** 4.1 또는 4.2를 실제로 해 본 뒤 남긴 기록 한 장. 고친 이유를 네 가지 원인으로 나눴을 때 어떤 원인이 가장 많았는지, 다음번에 이 기록을 열어 다시 했을 때 무엇이 빨라졌고 무엇이 여전히 손이 갔는지 적는다.

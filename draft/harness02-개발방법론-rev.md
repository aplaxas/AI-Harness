# AI 시대의 Harness 개발 방법론

## 1. Harness는 개발 흐름을 강제하는 환경이다

Harness는 AI에게 코드를 부탁하는 도구 모음이 아니라, 개발 판단과 산출물의 흐름을 지키게 하는 개발 환경이자 운영 원칙이다. AI는 빠르게 많은 선택지를 만들 수 있지만, 그 과정에서 합의, 검증, 맥락도 빠르게 잃을 수 있다. Harness는 그 세 가지를 단계마다 남긴다.

목적은 문서를 많이 만드는 일이 아니다. 대화에서 합의한 내용을 spec으로 바꾸고, spec을 검증 가능한 구현 순서로 바꾸며, 그 순서대로 테스트와 실제 코드를 만든다. 구현이 끝나면 실제 코드의 동작을 다시 읽어 흐름으로 복원하고, 이를 다음 작업에서 찾을 수 있는 지식으로 남긴다.

```text
brainstorming
  요구사항 합의와 spec
      ↓
writing-plans
  TDD를 내장한 구현 순서
      ↓
spec-explainer
  구현 전 사람의 이해와 검토
      ↓
subagent-driven-development
  테스트 코드와 실제 소스코드 생성
      ↓
spec-flow-e2e
  실제 소스코드를 정본으로 한 흐름 복원
      ↓
spec-wiki
  다음 작업에서 재사용할 프로젝트 지식
      ↺
다음 brainstorming의 컨텍스트
```

이 지도는 문서를 차례로 배달하는 컨베이어 벨트가 아니라 순환이다. `spec-wiki`가 만든 지식과 `spec-flow-e2e`가 실제 코드에서 복원한 흐름은 다음 `brainstorming`에서 질문의 질을 높이는 컨텍스트가 된다. 그러므로 어느 단계의 문서도 그 자체가 끝이 아니다.

## 2. Brainstorming — 무엇을 만들지 합의한다

### 왜 필요한가

SDD(Spec-Driven Development)는 긴 spec을 쓰는 일이 아니라, 구현 전에 서로 다른 해석을 찾아내는 규율이다. 사람, 사용자, AI가 같은 기능을 떠올리고 있는지 확인하지 않으면 AI는 그럴듯하지만 다른 것을 구현할 수 있다. 이 단계에서 DDD(Domain-Driven Design)의 출발점도 함께 잡는다. 애매한 도메인 용어는 추측하지 않고, 같은 단어를 같은 뜻으로 쓰도록 합의한다.

### AI에게 강제할 질문

AI는 목적, 범위, 제외 범위, 제약, 관찰 가능한 성공 조건을 묻는다. 예를 들어 “주문 취소”가 환불까지 포함하는지, 누가 취소할 수 있는지, 성공을 어떤 화면·응답·상태 변화로 확인하는지를 질문한다. 모호한 용어가 나오면 AI가 정의를 지어내지 않고 의미를 확인하게 한다.

### 사람이 확인할 것

사람은 기능의 목적과 우선순위, 받아들일 범위와 하지 않을 일을 승인한다. AI의 역할은 빈칸과 해석 차이를 드러내고 합의 내용을 기록하는 것이다. 결정의 책임까지 AI에게 넘기는 것이 아니다.

### 입력과 산출물

입력은 문제 상황, 사용자 요구, 현재 프로젝트의 제약과 이전 작업에서 축적한 지식이다. 산출물은 구현 전에 합의한 내용을 담은 spec이다. spec은 “무엇을 만들기로 했는가”의 구현 전 정본이다.

### 다음 단계로 넘기는 것

승인된 spec과 용어의 정의, 성공 조건을 `writing-plans`로 넘긴다. 다음 단계는 새로운 요구를 상상하는 곳이 아니라, 이 합의를 구현 가능한 순서로 나누는 곳이다.

### 주니어가 흔히 하는 오해

brainstorming을 자유로운 아이디어 회의로만 생각해 문서화된 spec 없이 끝내는 실수다. 좋은 대화를 했더라도 합의가 spec으로 남지 않으면 다음 작업자와 AI는 다시 추측해야 한다.

## 3. Writing Plans — 합의를 검증 가능한 구현 순서로 바꾼다

사용자가 흔히 `write-plan` 단계라고 부르는 흐름의 실제 skill 이름은 `superpowers:writing-plans`다. 이 단계는 spec을 하나의 큰 할 일로 두지 않고, 각각 독립적으로 구현하고 검토할 수 있는 작은 task로 분해한다.

### 왜 필요한가

합의된 요구가 있어도 구현 순서와 검증 방법이 없으면 작업은 즉흥적인 코드 생성으로 흐르기 쉽다. plan은 어떤 행동을 먼저 증명하고, 어떤 파일과 검증을 거쳐 다음 행동으로 갈지 정하는 실행 계약이다.

### AI에게 강제할 질문

AI는 각 task가 어떤 요구를 만족하는지, 어느 테스트로 증명하는지, 선행 task가 무엇인지 묻는다. 특히 TDD(Test-Driven Development)는 다음 순서로 plan 안에 구체화한다.

1. 실패하는 테스트 코드를 작성한다.
2. 테스트가 의도한 이유로 실패하는지 확인한다.
3. 테스트를 통과시키는 최소 실제 코드를 작성한다.
4. 관련 테스트를 실행해 통과를 확인한다.
5. 필요할 때만 리팩터링하고 다시 검증한다.

### 사람이 확인할 것

사람은 task의 순서가 위험을 일찍 드러내는지, 빠진 성공 조건은 없는지, 각 검증이 실제 요구를 보이는지 확인한다. 계획이 너무 크면 검토와 되돌리기가 어려우므로 더 작은 단위로 나눈다.

### 입력과 산출물

입력은 승인된 spec이다. 산출물은 task별 목적, 파일, 검증, 의존 순서를 담은 plan이다. plan은 spec을 따르며 구현 전에 “어떤 순서로 검증하며 만들 것인가”의 기준이 된다.

### 다음 단계로 넘기는 것

완성된 spec/plan pair를 `spec-explainer`로 넘긴다. 구현을 시작하기 전에 사람이 설계의 이유와 task 의존성을 이해할 기회를 만든다.

### 주니어가 흔히 하는 오해

상세한 plan을 작성한 것을 구현 완료로 착각하는 일이다. `writing-plans`는 테스트 코드나 실제 코드를 만들지 않는다. 그것들은 구현 단계가 지켜야 할 계약이다.

## 4. Spec Explainer — 구현 전에 사람이 이해하고 검토한다

### 왜 필요한가

spec과 plan은 정확해야 하지만, 때로는 밀도가 높아 주니어가 설계의 줄거리를 놓치기 쉽다. `spec-explainer`는 코드 생성 전에 사람이 왜 이 설계가 필요한지 이해하고 오해를 발견하게 하는 리뷰 장치다.

### AI에게 강제할 질문

AI는 왜 이 설계가 존재하는지, 어떤 대안이 왜 기각되었는지, plan의 task가 왜 그 의존 순서인지 풀어 설명한다. 설명을 매끄럽게 만드는 대신 원문에 없는 결정이나 요구를 추가해서는 안 된다.

### 사람이 확인할 것

사람은 설명을 통해 자신이 spec과 plan을 같은 뜻으로 읽고 있는지 확인하고, 구현 전에 누락과 잘못된 이해를 고친다. 특히 “왜 이 순서인가”가 납득되지 않으면 구현을 서두르지 않고 원문을 검토한다.

### 입력과 산출물

입력은 완료된 spec/plan pair다. 산출물은 `explains/<stem>-explained.md`다. 정본은 spec과 plan이며, explained 문서는 정본이 아니다. 설명과 원문이 다르면 spec과 plan을 따른다.

### 다음 단계로 넘기는 것

사람이 검토한 spec, plan, explained 문서를 구현 단계인 `subagent-driven-development`로 넘긴다. explained는 구현의 지시서가 아니라 이해를 돕는 동반 문서다.

### 주니어가 흔히 하는 오해

더 읽기 쉬운 해설만 읽고 원래 spec과 plan을 대체하는 실수다. 해설은 결정의 이유를 알려 주지만, 합의와 구현 순서의 정본은 여전히 원문 pair다.

## 5. Subagent-Driven Development — 테스트 코드와 실제 코드를 만든다

이 단계는 구현 전 문서 세계와 구현된 시스템을 잇는 명확한 전환점이다. `subagent-driven-development`는 테스트 코드와 production source code를 만든다.

### 왜 필요한가

spec과 plan이 원하는 동작을 말한다면, 이 단계는 그것을 실행 가능한 증거와 현재 시스템으로 바꾼다. 각 plan task를 작은 단위로 구현하므로, 실패 지점과 검토 범위를 좁힐 수 있다.

### AI에게 강제할 질문

AI는 한 task의 요구 행동을 먼저 실패하는 테스트로 표현한다. 그 실패는 원하는 행동이 우연히 이미 통과하고 있지 않음을 보여 준다. 이어서 그 행동만 통과시키는 최소 production code를 작성하고, 관련 테스트를 실행한다.

### 사람이 확인할 것

사람은 두 종류의 검토를 구분한다. 요구사항 검토는 code가 spec/plan에 맞는지 확인하고, 코드 품질 검토는 유지보수성, 경계, 이름, 오류 처리와 구현 품질을 확인한다. 많은 agent를 병렬로 돌렸거나 생성된 코드가 많다는 사실은 정확성의 증거가 아니다.

### 입력과 산출물

입력은 spec, plan, 그리고 이해를 보조하는 explained 문서다. 산출물은 task별 테스트 코드, 실제 소스코드, 테스트 실행 결과와 리뷰 기록이다. 통과한 테스트는 지정된 행동의 증거이며, 구현 후 현재 시스템이 어떻게 동작하는지를 설명하는 정본은 실제 소스코드다.

### 다음 단계로 넘기는 것

구현된 실제 소스코드와 테스트 결과를 `spec-flow-e2e`로 넘긴다. plan은 이제 구현을 읽을 파일을 찾는 지도일 뿐, 현재 동작 자체의 권위는 아니다.

### 주니어가 흔히 하는 오해

agent의 병렬성이나 생성된 코드의 양을 정확성의 증거로 해석하는 일이다. 정확성은 요구사항 적합성 검토, 코드 품질 검토, 그리고 실제 실행된 테스트로 확인한다.

```text
구현 전: spec과 plan이 만들려는 것의 기준
                  ↓
subagent-driven-development
테스트 코드 + 실제 소스코드 생성
                  ↓
구현 후: 실제 소스코드가 현재 동작의 기준
```

## 6. Spec Flow E2E — 실제 코드에서 시스템 흐름을 복원한다

### 왜 필요한가

구현이 끝난 뒤에는 계획이 아니라 실제 코드가 현재의 동작을 말한다. `spec-flow-e2e`는 Playwright나 Cypress E2E 테스트 코드를 생성하는 skill이 아니다. production source code를 읽어 시스템 흐름을 복원하는 구현 후 문서화 단계다.

### AI에게 강제할 질문

AI는 front → back → db → back → front의 흐름을 실제 파일에서 추적한다. 진입점, 권한·검증 같은 gate, 실패 시의 동작, transaction과 persistence 순서, 디버깅을 시작할 파일과 로그 지점을 찾는다. plan은 관련 파일을 찾는 지도일 뿐 실제 동작의 정본은 아니다.

### 사람이 확인할 것

사람은 spec, plan, explained 문서와 구현 사이에 차이가 있는지 확인한다. 차이는 숨길 흠이 아니라 보고해야 할 핵심 발견이다. 의도된 구현 변경인지, 요구에서 벗어난 것인지 판단할 수 있게 차이를 드러낸다.

### 입력과 산출물

입력은 plan과 구현된 source code다. 산출물은 `e2e/<stem>-e2e.md`다. e2e 문서의 정본은 production source code이며, plan·spec·explained 문서는 현재 동작의 권위가 아니다.

### 다음 단계로 넘기는 것

전체 구조를 알고 싶은 사람과 사람 또는 AI가 디버깅을 시작할 때 쓰는 흐름 문서를 `spec-wiki`로 넘긴다. 이 문서가 있어야 위키는 “지금 어떻게 도나”를 실제 코드에 근거해 쓸 수 있다.

### 주니어가 흔히 하는 오해

구현된 source files를 열지 않고 plan에 있던 class name과 code snippet을 복사하는 일이다. 계획과 코드가 다를 수 있으므로, 흐름은 반드시 구현된 파일에서 다시 읽어야 한다.

## 7. Spec Wiki — 끝난 작업을 다음 작업의 지식으로 바꾼다

### 왜 필요한가

완료된 작업의 결정, 계획, 설명, 실제 흐름이 여러 폴더에 흩어져 있으면 다음 사람과 AI는 같은 조사를 반복한다. `spec-wiki`는 한 stem을 공유하는 spec, plan, explained, e2e 문서를 연결해 찾을 수 있는 프로젝트 지식으로 바꾼다.

### AI에게 강제할 질문

AI는 네 종류의 원문을 같은 stem으로 묶고, 현재 동작의 설명에 e2e가 실제로 있는지 확인한다. `지금 어떻게 도나`는 e2e 문서에서만 쓸 수 있다. e2e가 없으면 빈칸을 상상으로 채우지 않고 그 부재를 보이게 남긴다.

### 사람이 확인할 것

사람은 위키가 원문을 요약한 탐색 도구임을 확인하고, 필요한 판단은 연결된 정본으로 돌아가 검증한다. spec/plan/explained/e2e 각각의 정본 관계는 위키가 생겨도 바뀌지 않는다.

### 입력과 산출물

입력은 같은 stem의 spec, plan, explained, e2e 문서다. 산출물은 `wiki/<stem>-wiki.md`, `wiki/index.md`, `wiki/index.json`, `dashboard.html`이다. 이 작업은 source documents를 이동하거나 수정하지 않으며, wiki도 정본이 아니다. 원문 네 종류는 각자의 정본 관계를 계속 유지한다.

### 다음 단계로 넘기는 것

원문 해시를 이용한 incremental regeneration은 바뀐 지식만 다시 만들어, 변하지 않은 페이지를 불필요하게 덮어쓰지 않는다. 이렇게 최신성을 유지한 위키와 색인은 이후 사람과 AI가 검색해 다음 `brainstorming`의 컨텍스트로 사용한다.

### 주니어가 흔히 하는 오해

위키 요약이 존재한다는 사실만으로 구현과 문서가 최신이라고 믿는 일이다. 원문의 정본 관계와 최신 상태를 확인해야 하며, e2e가 빠진 경우에는 현재 동작에 관한 지식도 비어 있음을 인정해야 한다.

## 8. 방법론은 독립된 구호가 아니라 흐름 안의 규율이다

SDD, DDD, TDD는 각각 따로 외우는 구호가 아니라 여섯 단계에서 반복해 실행하는 판단 규율이다.

| 방법론 | 작동하는 주요 단계 | 강제하는 판단 | 남는 증거 |
| --- | --- | --- | --- |
| SDD | brainstorming, writing-plans에서 요구의 해석 차이를 먼저 드러내고 구현 순서로 고정한다. | 무엇을 만들며 성공을 어떻게 확인하는가를 범위·제외 범위·관찰 가능한 조건으로 결정한다. | 합의된 spec과 이를 검증 단위로 나눈 plan이 남는다. |
| DDD | brainstorming부터 전체 흐름에서 용어를 묻고, 문서·테스트·코드가 같은 의미를 유지하게 한다. | 같은 용어를 같은 뜻으로 쓰는가, 애매한 도메인 단어를 추측하지 않았는가를 판단한다. | 합의된 용어가 반영된 모든 산출물이 남는다. |
| TDD | writing-plans, subagent-driven-development에서 계획과 구현의 피드백 순서를 강제한다. | 원하는 행동을 실패 테스트부터 증명하고 최소 실제 코드로 통과시켰는가를 판단한다. | 테스트 코드, 실행 결과, 최소 실제 코드가 남는다. |

Deep Module을 네 번째 중심 기둥으로 둘 필요는 없다. 그것이 틀린 생각이어서가 아니라, AI 시대의 Harness에서 더 먼저 강제해야 할 것은 합의, 검증, 정본 전환, 지식 환류이기 때문이다. 다만 구현 후 코드 리뷰와 흐름 이해에서는 “호출자가 알아야 할 복잡성을 줄였는가?”라는 질문이 여전히 유용하다. 이 질문은 모듈 경계와 유지보수성을 검토하는 데 쓴다.

사람이 모든 인터페이스를 완전히 선언해야만 AI가 코드를 만들 수 있다는 가정도 버린다. 사람은 목적, 의미, 승인, 판단을 책임지고, AI는 질문·계획·구현·검증을 돕는다. Harness는 AI가 만든 구현이 합의된 의도, 실행 가능한 검증, 실제 실행 구조, 재사용 가능한 프로젝트 지식에 계속 연결되도록 보장한다.

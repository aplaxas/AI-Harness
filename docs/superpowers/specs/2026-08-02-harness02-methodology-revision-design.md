# Harness 개발 방법론 전면 개정 설계

## 1. 목적

기존 `draft/harness02-개발방법론.md`는 보존한다. 새 문서는 `draft/harness02-개발방법론-rev.md`로 만들고, 기존의 SDD·DDD·TDD·Deep Module별 구성을 실제 Harness의 여섯 단계 중심 구성으로 전면 개정한다.

주 독자는 주니어 개발자다. 스킬 사용법만 나열하지 않고, 각 단계가 왜 필요하며 어떤 판단과 산출물을 다음 단계로 넘기는지 설명한다.

## 2. 중심 주장

AI 시대의 개발자는 모든 인터페이스와 내부 설계를 미리 완성한 뒤 AI에게 구현만 맡기는 사람이 아니다. 사람과 AI가 함께 요구사항을 합의하고, 구현 순서를 검증하며, 테스트 코드와 실제 소스코드를 생성하고, 구현된 코드에서 실제 흐름을 다시 복원해 다음 작업의 지식으로 돌려놓는 개발 흐름을 설계한다.

Harness는 단순한 스킬 모음이 아니다. 이 흐름에서 지켜야 할 질문, 검증 순서, 정본 관계와 산출물을 강제하는 개발 환경이자 운영 원칙이다.

## 3. 전체 흐름

```text
brainstorming
  요구사항 합의와 spec
      ↓
writing-plans
  TDD를 내장한 구현 순서
      ↓
spec-explainer
  구현 전 사람의 이해와 검토
      ↓
subagent-driven-development
  테스트 코드와 실제 소스코드 생성
      ↓
spec-flow-e2e
  실제 소스코드를 정본으로 한 흐름 복원
      ↓
spec-wiki
  다음 작업에서 재사용할 프로젝트 지식
      ↺
다음 brainstorming의 컨텍스트
```

문서는 이 흐름을 일방향 파이프라인이 아니라 순환 구조로 설명한다. 마지막에 만들어진 프로젝트 지식은 다음 기능의 brainstorming에서 다시 컨텍스트로 사용된다.

실제 스킬명은 `superpowers:writing-plans`로 표기한다. 사용자가 부르는 흐름 이름인 `write-plan`과 실제 스킬명이 다름은 첫 등장 때 짧게 설명한다.

## 4. 장 구성

### 4.1 AI 시대의 Harness

Harness를 개발 판단과 산출물의 흐름을 강제하는 환경으로 정의한다. 문서를 많이 만드는 것이 목적이 아니라, AI 작업에서 잃기 쉬운 합의·검증·맥락을 단계별로 보존하는 것이 목적임을 밝힌다.

### 4.2 Brainstorming — 무엇을 만들지 합의한다

SDD를 중심으로 목적, 범위, 제약, 성공 조건을 질문하고 spec으로 고정한다. DDD의 유비쿼터스 언어도 이 단계부터 적용하여 사람과 AI가 같은 용어를 같은 뜻으로 사용하게 한다.

### 4.3 Writing Plans — 구현 가능한 순서로 바꾼다

spec을 작은 구현 단계로 변환한다. 각 단계에 실패 테스트, 최소 구현, 검증, 필요한 리팩터링을 넣어 TDD를 별도 구호가 아니라 실행 계약으로 만든다.

### 4.4 Spec Explainer — 구현 전에 사람이 이해한다

spec과 plan을 주니어가 읽을 수 있는 줄거리로 푼다. 해설은 정본이 아니다. 설계 이유, 기각한 대안, task 순서의 의존성을 이해하고 구현 전에 오류를 발견하게 하는 리뷰 장치다.

### 4.5 Subagent-Driven Development — 계획을 코드로 만든다

plan의 task를 작은 검증 단위로 실행하여 테스트 코드와 실제 소스코드를 생성한다. 실패하는 테스트가 요구 행동을 먼저 고정하고, 최소 실제 코드가 이를 통과시킨다. task별 요구사항 적합성 검토와 코드 품질 검토로 누적 오류를 줄인다.

이 단계가 구현 전 문서 세계와 구현 후 실제 시스템을 가르는 전환점이다.

### 4.6 Spec Flow E2E — 실제 코드에서 흐름을 복원한다

plan은 읽어야 할 소스를 찾는 지도이고, 실제 소스코드는 현재 동작의 정본이다. 구현 후 `front → back → db → back → front` 흐름, 게이트, 실패 조건, 영속화 순서를 복원한다.

plan과 실제 코드가 어긋난 지점은 숨길 오류가 아니다. 구현 중 생긴 변경이 의도된 것인지 되돌려야 할 것인지 사람이 판단할 수 있도록 드러내는 것이 이 단계의 핵심 수확이다. 이 문서의 우선 독자는 전체를 조망하려는 사람이며, 동시에 사람과 AI의 디버깅 진입점으로 사용한다.

### 4.7 Spec Wiki — 작업 기록을 프로젝트 지식으로 바꾼다

같은 stem의 spec·plan·explained·e2e를 한 위키 페이지로 합성한다. 원문을 이동하거나 수정하지 않으며, 위키 자체도 정본이 아니다. 색인과 관련 링크를 통해 다음 사람과 AI가 과거 결정, 현재 제약, 구현 흐름을 찾게 한다.

### 4.8 방법론이 흐름 안에서 작동하는 위치

SDD·DDD·TDD를 독립 이론 장으로 반복하지 않는다. 각 단계에서 어떤 질문과 행동으로 구현되는지를 하나의 표로 정리한다.

Deep Module은 핵심 방법론 목록에서 제외한다. 다만 복잡성을 이해 가능한 경계로 관리한다는 통찰은 유효하므로, 실제 코드를 사후 복원하고 모듈 경계를 검토하는 제한된 맥락에서만 언급한다. 사람이 모든 인터페이스를 미리 완성해야 한다는 전제로 사용하지 않는다.

## 5. 산출물과 정본 관계

| 단계 | 핵심 질문 | 산출물 | 기준 |
| --- | --- | --- | --- |
| brainstorming | 무엇을 왜 만드는가? | spec | 사용자와 AI가 합의한 요구사항 |
| writing-plans | 어떤 순서로 검증하며 구현하는가? | plan | spec |
| spec-explainer | 설계와 구현 순서를 사람이 이해했는가? | explained | spec·plan |
| subagent-driven-development | 계획한 행동을 코드로 어떻게 증명하는가? | 테스트 코드와 실제 소스코드 | spec·plan, 실행되는 테스트 |
| spec-flow-e2e | 생성된 소스코드는 실제로 어떻게 동작하는가? | e2e 흐름 문서 | 실제 소스코드 |
| spec-wiki | 전체 작업 지식을 어떻게 다시 찾는가? | wiki·색인·대시보드 | spec·plan·explained·e2e 원문 |

정본은 시점과 질문에 따라 달라진다.

- 구현 전, 만들려는 것의 기준은 spec과 plan이다.
- `subagent-driven-development`에서 테스트 코드와 실제 소스코드가 생성된다.
- 테스트 코드는 요구 행동이 검증되었다는 실행 가능한 근거다.
- 구현 후 현재 시스템의 실제 동작을 설명할 때는 소스코드가 정본이다.
- explained와 wiki는 이해와 탐색을 돕지만 정본이 아니다.
- plan과 코드의 차이는 검토해야 할 정보다.

## 6. 각 장의 반복 형식

여섯 단계의 장은 가능한 한 같은 질문 구조를 사용한다.

1. 이 단계가 필요한 이유
2. AI에게 강제할 질문
3. 사람이 확인할 것
4. 입력과 산출물
5. 다음 단계로 넘기는 것
6. 주니어가 흔히 하는 오해

반복 형식을 통해 주니어 독자가 스킬 이름보다 개발 판단의 리듬을 먼저 익히게 한다.

## 7. 문체와 범위

- 현재 문서와 같은 설명형 `~다`체를 사용한다.
- 주니어가 처음 만나는 용어는 첫 등장 때 정의한다.
- 실제 스킬명과 산출물 경로는 흐름을 이해하는 데 필요한 만큼만 쓴다.
- spec-tools README와 각 SKILL의 정본 규칙을 정확히 반영한다.
- 영상 추천 목록은 새 문서에서 제거하여 핵심 흐름을 끊지 않는다.
- 특정 기능의 긴 예시는 만들지 않는다. 필요한 경우 한두 문장의 짧은 예시만 사용한다.
- 기존 `draft/harness02-개발방법론.md`는 수정하지 않는다.

## 8. 완료 기준

- 새 문서가 여섯 단계를 장의 순서로 사용한다.
- SDD·DDD·TDD가 실제로 작동하는 단계와 질문이 드러난다.
- `subagent-driven-development`의 산출물이 테스트 코드와 실제 소스코드임을 명시한다.
- 구현 전과 구현 후의 정본 전환을 주니어가 구분할 수 있다.
- `spec-explainer`와 `spec-wiki`가 정본이 아님을 명시한다.
- `spec-flow-e2e`가 e2e 테스트 생성 스킬이 아니라 실제 코드 흐름 복원 스킬임을 명시한다.
- Deep Module을 중심 방법론으로 유지하지 않는다.
- 마지막 산출물이 다음 brainstorming의 컨텍스트로 돌아가는 순환 구조가 드러난다.
